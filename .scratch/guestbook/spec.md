# Spec: 미니 방명록

Status: ready-for-agent

## Problem Statement

방문자는 회원가입이나 로그인 없이 이름과 한마디를 남기고, 다른 사람들이 남긴 글을 최신순으로 보고 싶다. 그러면서도 자기가 남긴 글은 자기만 고치거나 지울 수 있어야 한다. 계정이 없으므로, 글을 쓸 때 정한 비밀번호가 본인임을 증명하는 유일한 수단이다. 비밀번호가 틀리면 수정이나 삭제가 거부되고, 사용자는 그 사실을 분명히 안내받아야 한다.

## Solution

한 페이지짜리 방명록이다. 위쪽에는 작성 폼이 있고 아래쪽에는 모든 **글(Entry)** 이 작성 시각 최신순으로 쌓인다.

- 누구나 **작성자 이름(Author name)**, **메시지(Message)**, **비밀번호(Entry password)** 를 입력해 글을 남길 수 있다.
- 각 글 카드에서 "수정"이나 "삭제"를 누르면 카드 안에 비밀번호 입력란이 펼쳐진다.
  - 비밀번호가 맞으면 메시지가 수정되거나 글이 삭제된다.
  - 틀리면 카드 안에 거부 사유가 표시되고, 입력한 내용은 그대로 남는다.
- 헤더에 개발자 이름 **강동헌** 과 학번 **202204169** 가 항상 표시된다.
- Next.js(App Router)와 TypeScript로 만들고, Neon Postgres를 사용하며, Vercel에 배포한다.

## User Stories

1. 방문자로서, 가입이나 로그인 없이 방명록 페이지에 바로 들어가고 싶다. 그래야 부담 없이 글을 남길 수 있다.
2. 방문자로서, 작성자 이름, 메시지, 비밀번호를 입력해 새 글을 남기고 싶다. 그래야 내 흔적을 남길 수 있다.
3. 방문자로서, 글을 남기면 바로 목록 맨 위에서 내 글을 보고 싶다. 그래야 제대로 등록됐는지 알 수 있다.
4. 방문자로서, 글을 남긴 뒤 이름 칸은 그대로 남아 있었으면 한다. 그래야 이어서 글을 쓸 때 다시 입력하지 않아도 된다.
5. 방문자로서, 글을 남긴 뒤 메시지 칸과 비밀번호 칸은 비워졌으면 한다. 그래야 같은 글을 실수로 다시 보내지 않고, 비밀번호가 화면에 남지 않는다.
6. 방문자로서, 이름이나 메시지를 비워 두거나 공백만 넣으면 어느 칸이 문제인지 안내받고 싶다. 그래야 고쳐서 다시 보낼 수 있다.
7. 방문자로서, 이름이 20자, 메시지가 500자를 넘으면 안내받고 싶다. 그래야 제한을 알 수 있다.
8. 방문자로서, 비밀번호가 4자보다 짧거나 72자보다 길면 안내받고 싶다. 그래야 쓸 수 있는 비밀번호를 정할 수 있다.
9. 방문자로서, 입력이 거부됐을 때 내가 쓴 메시지가 지워지지 않았으면 한다. 그래야 긴 글을 다시 쓰지 않아도 된다.
10. 방문자로서, 메시지에 줄바꿈을 넣으면 목록에서도 줄바꿈이 유지됐으면 한다. 그래야 내가 쓴 모양 그대로 보인다.
11. 방문자로서, 다른 사람과 같은 이름으로도 글을 쓸 수 있었으면 한다. 이름은 표시용일 뿐 신원이 아니기 때문이다.
12. 방문자로서, 전체 글 목록을 최신 작성 순으로 보고 싶다. 그래야 최근 글을 먼저 읽을 수 있다.
13. 방문자로서, 각 글의 작성자 이름, 메시지, 작성 시각을 보고 싶다. 그래야 누가 언제 무슨 말을 남겼는지 알 수 있다.
14. 방문자로서, 작성 시각이 한국 시간 기준 `2026-09-30 14:03` 형식으로 보였으면 한다. 그래야 헷갈리지 않는다.
15. 방문자로서, 글이 하나도 없을 때는 빈 목록 대신 첫 글을 남겨 달라는 안내를 보고 싶다. 그래야 페이지가 고장 난 게 아님을 알 수 있다.
16. 방문자로서, 수정된 글에 "(수정됨)"과 수정 시각이 붙었으면 한다. 그래야 처음 쓴 그대로의 글이 아니라는 것을 알 수 있다.
17. 방문자로서, 수정된 글도 원래 작성 시각 자리에 있었으면 한다. 그래야 수정 때문에 목록 순서가 바뀌지 않는다.
18. 글쓴이로서, 내 글 카드의 "수정"을 누르면 현재 메시지가 채워진 입력창과 비밀번호 입력란이 카드 안에 열렸으면 한다. 그래야 페이지를 떠나지 않고 고칠 수 있다.
19. 글쓴이로서, 새 메시지와 비밀번호를 한 번에 제출해 수정하고 싶다. 그래야 과정이 한 번으로 끝난다.
20. 글쓴이로서, 비밀번호가 맞으면 수정된 메시지가 바로 목록에 반영됐으면 한다. 그래야 결과를 즉시 확인할 수 있다.
21. 글쓴이로서, 수정할 때 비밀번호가 틀리면 수정이 거부되고 "비밀번호가 일치하지 않습니다" 같은 안내가 카드 안에 보였으면 한다. 그래야 왜 반영되지 않았는지 알 수 있다.
22. 글쓴이로서, 비밀번호가 틀려 수정이 거부돼도 고쳐 쓴 메시지가 입력창에 남아 있었으면 한다. 그래야 비밀번호만 다시 입력하면 된다.
23. 글쓴이로서, 수정할 때도 메시지 길이 제한이 똑같이 적용되고 안내받고 싶다. 그래야 작성할 때와 규칙이 같다.
24. 글쓴이로서, 수정 중에 "취소"를 눌러 원래 카드 모습으로 돌아가고 싶다. 그래야 마음이 바뀌었을 때 아무것도 바뀌지 않는다.
25. 글쓴이로서, 작성자 이름은 수정할 수 없고 메시지만 수정할 수 있다는 것을 화면에서 알 수 있었으면 한다. 그래야 헷갈리지 않는다.
26. 글쓴이로서, 내 글 카드의 "삭제"를 누르면 카드 안에 비밀번호 입력란과 삭제 버튼이 열렸으면 한다. 그래야 페이지를 떠나지 않고 지울 수 있다.
27. 글쓴이로서, 비밀번호가 맞으면 글이 목록에서 바로 사라졌으면 한다. 그래야 삭제된 것을 확인할 수 있다.
28. 글쓴이로서, 삭제할 때 비밀번호가 틀리면 삭제가 거부되고 그 사실이 카드 안에 안내됐으면 한다. 그래야 글이 남아 있는 이유를 알 수 있다.
29. 글쓴이로서, 비밀번호 입력과 삭제 버튼 클릭만으로 삭제가 끝났으면 한다. 비밀번호 입력 자체가 확인 절차이므로 추가 확인 창은 필요 없다.
30. 방문자로서, 다른 탭에서 이미 삭제된 글을 수정하거나 삭제하려 하면 비밀번호 오류와는 다른 "이미 삭제된 글입니다" 안내를 보고 싶다. 목록도 새로 고쳐져야 한다. 그래야 상황을 정확히 알 수 있다.
31. 방문자로서, 제출하는 동안에는 버튼이 비활성화되고 처리 중임이 표시됐으면 한다. 그래야 두 번 누르지 않는다.
32. 방문자로서, 비밀번호가 입력할 때 가려졌으면 한다. 그래야 옆 사람이 보지 못한다.
33. 방문자로서, 휴대폰에서도 가로 스크롤 없이 폼과 목록을 쓸 수 있었으면 한다. 그래야 어디서든 쓸 수 있다.
34. 방문자로서, 시스템이 다크 모드일 때 방명록도 어둡게 보였으면 한다. 그래야 눈이 편하다.
35. 채점자로서, 헤더에서 개발자 이름 "강동헌"과 학번 "202204169"를 바로 확인하고 싶다. 그래야 누구의 과제인지 알 수 있다.
36. 글쓴이로서, 내 비밀번호가 원문으로 저장되거나 브라우저로 보내지지 않았으면 한다. 그래야 DB가 유출돼도 비밀번호가 드러나지 않는다.
37. 방문자로서, 다른 사람이 입력한 메시지에 HTML이나 스크립트가 들어 있어도 글자 그대로만 보였으면 한다. 그래야 페이지가 조작되지 않는다.
38. 개발자로서, 명령 하나로 Neon에 테이블을 만들고 싶다. 그래야 새 환경을 빠르게 준비할 수 있다.
39. 개발자로서, `DATABASE_URL` 환경 변수만 설정하면 로컬과 Vercel에서 똑같이 동작했으면 한다. 그래야 배포가 단순해진다.

## Implementation Decisions

### 도메인

- 용어는 `GLOSSARY.md`를 따른다. **Entry**, **Message**, **Author name**, **Entry password** 이다.
- 권한은 글 단위로만 판단한다. 수정이나 삭제 요청은 그 글의 비밀번호와 대조하며, 작성자 이름은 권한과 무관하다.
- 글에서 수정할 수 있는 것은 메시지뿐이다.
- 삭제는 완전 삭제이며, 복구할 수 없다.

### 방명록 모듈 (핵심 모듈, 유일한 테스트 경계)

- 방명록 동작 전체를 하나의 깊은 모듈에 모은다. 이 모듈은 저장소 인터페이스(`EntryStore`)를 주입받는다.
- 모듈의 공개 동작은 네 가지다.
  - 글 목록: 작성 시각 최신순
  - 글 작성: 입력값 `{ authorName, message, password }`
  - 메시지 수정: 입력값 `{ id, message, password }`
  - 글 삭제: 입력값 `{ id, password }`
- 쓰기 동작은 예외를 던지지 않고, 판별 가능한 결과 하나를 돌려준다.
  - `ok`: 성공
  - `invalid`: 필드별 오류 메시지를 담는다
  - `wrong-password`: 비밀번호 불일치
  - `not-found`: 없거나 이미 삭제된 글
- 입력 검증은 이 모듈 안에서 한다.
  - 이름은 앞뒤 공백을 제거한 뒤 1~20자
  - 메시지는 앞뒤 공백을 제거한 뒤 1~500자이며, 내부 줄바꿈은 유지한다
  - 비밀번호는 4~72자이며, 공백을 제거하지 않는다
  - 글자 수는 사용자가 보는 글자 기준으로 센다
- 비밀번호는 Node 내장 `crypto.scrypt`로 해시한다.
  - 글마다 무작위 salt를 쓴다.
  - 비교는 `timingSafeEqual`로 한다.
  - 저장 형식에 salt를 함께 담는다. 예: `scrypt$<salt>$<hash>`
- 비밀번호 해시는 모듈 밖으로 나가지 않는다. 목록 결과와 모든 반환값에서 해시를 제외한다.
- 모듈이 돌려주는 글의 모양: `{ id, authorName, message, createdAt, updatedAt | null }`

### 저장소

- Neon Postgres에 `entries` 테이블 하나를 둔다. 컬럼은 다음과 같다.
  - `id`: `bigint GENERATED ALWAYS AS IDENTITY`, 기본 키
  - `author_name`: `text NOT NULL`
  - `message`: `text NOT NULL`
  - `password_hash`: `text NOT NULL`
  - `created_at`: `timestamptz NOT NULL DEFAULT now()`
  - `updated_at`: `timestamptz NULL`. 한 번도 수정되지 않은 글은 NULL이다.
- `created_at DESC`로 조회한다. 인덱스는 있으면 좋지만 필수는 아니다.
- 스키마는 SQL 파일 하나로 관리한다. `npm run db:init` 스크립트가 `DATABASE_URL`에 연결해 이 파일을 실행한다. `CREATE TABLE IF NOT EXISTS`로 작성해 여러 번 실행해도 안전하게 만든다.
- 운영용 `EntryStore` 구현은 `@neondatabase/serverless`의 태그드 템플릿 SQL을 쓴다. ORM은 쓰지 않는다. 모든 값은 파라미터로 바인딩한다.
- 메시지 수정과 삭제에서 경쟁 상태가 생길 수 있다. 비밀번호를 확인한 사이에 글이 지워지면, 수정·삭제 쿼리의 영향 행 수가 0이 된다. 이 경우 `not-found`로 처리한다.

### Next.js 레이어 (얇은 어댑터)

- 이 버전의 Next.js는 학습 데이터와 다를 수 있다. 구현 전에 `node_modules/next/dist/docs/`에서 Server Actions, `useActionState`, `revalidatePath`, 캐싱 관련 문서를 먼저 확인한다.
- 목록 조회는 페이지 Server Component에서 방명록 모듈을 직접 호출한다. 페이지는 요청마다 새로 렌더링되도록 설정해 캐시된 목록이 보이지 않게 한다.
- 작성, 수정, 삭제는 Server Action이다.
  - 각 Action은 `FormData`를 모듈 입력으로 바꾸고, 모듈을 호출한 뒤, 결과를 폼 상태로 돌려준다.
  - `ok`나 `not-found`면 목록을 재검증한다.
- Route Handler는 만들지 않는다.
- 클라이언트 컴포넌트는 폼 상태가 필요한 부분에만 쓴다.
  - 작성 폼
  - 글 카드: 보기, 수정, 삭제 모드를 전환한다
  - 제출 중 상태는 `useActionState`와 pending 상태로 표시한다.
- 오류 표시
  - `invalid`: 해당 필드 옆에 표시한다.
  - `wrong-password`: 카드 안에 "비밀번호가 일치하지 않습니다"를 표시하고, 입력한 메시지는 유지한다.
  - `not-found`: "이미 삭제된 글입니다"를 표시하고 목록을 새로 고친다.
- 작성에 성공하면 메시지와 비밀번호 칸을 비우고 이름 칸은 남긴다.
- 날짜는 서버에서 `Asia/Seoul` 기준 `YYYY-MM-DD HH:mm`으로 포맷해 hydration 불일치를 피한다.

### UI

- 한 열 카드 레이아웃이며 Tailwind를 쓴다(이미 설치됨).
  - 헤더: 제목, 그리고 "강동헌 · 202204169"
  - 작성 폼
  - 글 목록
  - 빈 목록 안내
- 메시지는 줄바꿈을 유지해 표시한다(`white-space: pre-wrap` 계열). React 기본 이스케이프에 맡기고, HTML을 직접 삽입하지 않는다.
- 모바일 폭과 다크 모드(`prefers-color-scheme`)를 지원한다.
- 비밀번호 입력란은 `type="password"`이고 `autocomplete`로 브라우저 저장을 유도하지 않는다.
- 페이지 메타데이터(제목, 설명)는 방명록에 맞게 바꾼다.

### 배포

- Vercel에 배포한다. `DATABASE_URL`을 Vercel 프로젝트 환경 변수로 등록한다.
- 서버 코드는 Node 런타임에서 실행한다. `crypto.scrypt`를 쓰므로 Edge 런타임을 쓰지 않는다.

## Testing Decisions

- 좋은 테스트는 모듈의 외부 동작만 확인한다. "틀린 비밀번호로 수정하면 거부되고 메시지는 그대로다"처럼 공개 동작과 결과로 검증한다. 해시 형식, SQL, 내부 함수 호출 여부 같은 구현 세부는 검증하지 않는다.
- 테스트 경계는 **방명록 모듈 하나**다. Vitest를 새로 도입하고, 메모리 기반 `EntryStore`를 주입해 모듈을 테스트한다. 실제 DB, Server Action, React 컴포넌트는 테스트하지 않는다. 이들은 얇은 어댑터이므로 직접 확인한다.
- 다룰 동작
  - 작성 후 목록에 나타나고, 목록은 작성 시각 최신순이다.
  - 입력 검증의 경계값: 0자, 공백만 입력, 20/21자, 500/501자, 비밀번호 3/4/72/73자
  - 맞는 비밀번호로 메시지를 수정하면 반영되고 `updatedAt`이 채워지며, 목록 순서는 바뀌지 않는다.
  - 틀린 비밀번호로 수정하면 `wrong-password`이고 메시지는 그대로다.
  - 맞는 비밀번호로 삭제하면 목록에서 사라진다.
  - 틀린 비밀번호로 삭제하면 `wrong-password`이고 글은 남아 있다.
  - 없는 id를 수정하거나 삭제하면 `not-found`다.
  - 같은 작성자 이름이지만 다른 비밀번호로 쓴 두 글은 서로의 비밀번호로 수정되거나 삭제되지 않는다.
  - 어떤 반환값에도 비밀번호나 해시가 포함되지 않는다.
- 기존 테스트가 없으므로 참고할 선례(prior art)는 없다. 이 모듈 테스트가 첫 선례가 된다. `npm test` 스크립트를 추가한다.

## Out of Scope

- 회원가입, 로그인, 세션, 관리자 기능
- 작성자 이름 수정
- 비밀번호 변경이나 분실 복구
- 비밀번호 무차별 대입 방지(시도 횟수 제한). 서버리스 환경에서는 별도 상태 저장소가 필요해 과제 범위를 넘는다. 제외 사유를 README에 적는다.
- 페이지네이션, 검색, 필터
- 소프트 삭제와 복구
- 스팸 방지(CAPTCHA 등)
- 실제 DB 통합 테스트와 E2E 테스트
- 실시간 갱신(다른 사용자의 새 글 자동 표시)
